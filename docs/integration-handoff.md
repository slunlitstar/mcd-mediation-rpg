# 本轮提交与前后端联调交接

## 当前集成（2026-10-25）

最新修正：复议已从“原餐再加一个单品”改成“目标成员整餐重新组合”。保留个人预算、排除项、硬性要求以及其他成员餐品；最多对八个候选组合真实试算，成功显示换入／换出的餐品和实付变化。当前已含的食物类别在复议选项中标记；“更饿了”增加主餐或配餐份数，不承诺饱腹。复议只更新当前方案，其他策略未重新生成。

真实验证采用北京宣武门外大街餐厅、三人预算 ¥30／¥40／¥20：成员1由 ¥26 的吉士汉堡包套餐改为 ¥28 的“堡”你欢乐套餐；其他两位餐品保持，整单 6800 分等于成员分摊合计。仅试算，未创建订单。

当前开发分支为 `codex/integration`。网页已通过服务端接入真实门店、菜单、试算与模型推荐；模型失败时保留规则降级。下面的第一轮记录为历史说明。

本轮新增三项：

- **无解建议**：先联合选择主餐与必点食物，避免贪心选择导致假无解。确实无解时，最多给出两条经过真实试算的调整建议，明确列出预算或食物选择的变化。点击后直接采用已试算的方案；不自动改条件，也不放宽忌辣／忌牛肉要求。建议报价超过五分钟需重新生成；未能验证时只提示调整或换店。
- **刷新保留**：同一浏览器本地保存门店、成员角色、预算、偏好、自填文字和当前成员，期限 24 小时。刷新后首页可继续填写。价格、已接受状态、模型请求与服务端凭据不保存；回到结果前重新查询试算。不需要数据库。
- **默认套餐**：服务端查询 `query-meal-detail`，只解析明确标记的默认子项，把 `roundList` 传给 `calculate-price`。套餐子项参与必点类别、不喜欢类别和食材推导的检查；不重复添加已有薯条／饮品。无法确认默认组成的套餐暂不推荐。结果页显示默认套餐标签与组成，目前不支持换饮料、换小食。

接口增量见 [mediate-contract.md](mediate-contract.md) 的「无解建议与默认套餐」章节。策略比较、保存图片本轮没有增加。

验证：离线单元测试、前后端 HTTP 联调及真实 MCP 查询／试算均已执行；真实样例中 16 个套餐默认组成可解析，套餐应付 6200 分、分摊合计 6200 分，预算不足时可返回提高预算的可行建议。手机真机的视觉与触控验收仍需人工完成。

## 两位开发者的提交顺序

1. 各自在自己的分支提交当前工作，推送到同一个仓库的不同分支；推送后仍可继续开发。
2. 前端使用 `codex/demo-round-one`；后端保留已有独立分支。若后端正在 main 或前端同名分支，先从当前工作状态建立独立后端分支，例如 `codex/backend-round-two`，不要丢弃本地改动。
3. 各自建立面向 `main` 的 PR，说明本轮范围、检查结果和运行方法。先保留 PR 供比较，避免未经检查直接合并两份工作。
4. 双方先对齐后端接口与样例，再逐个合并 PR；第二个 PR 必须基于合并后的 main 检查冲突并重新验证。
5. 两个 PR 合并后，各自保存工作分支上的后续改动，再更新本地 main，从最新 main 开始接口接入。

## 后端 AI 需要交付

- 已实现的功能、所在分支及 PR 地址。
- 启动命令、运行环境、需要的环境变量名称（示例文件不含实际凭据）。
- 网页可调用的接口地址、HTTP 方法、请求与响应 JSON 样例；成功、无解、临时失败各一例。
- 门店与商品数据获取方式，价格单位、商品 ID、图片、可用性和食材信息的真实来源。
- MCP 已验证的工具能力、尚未支持的能力及所需授权；区分“编辑器里能调用 MCP”和“网页可通过服务端接口调用”。
- 方案与复议是否已经实现；未实现的部分写明，不冒充已完成。

金额约定：个人输入 `budget` 为元，餐品与方案金额使用整数分。真实商品 ID 必须匹配返回的真实商品目录。
MCP 配置、Token 和密钥留在服务端，不能写入网页资源、提交或示例 JSON。
不要为了配合前端先重写 UI；契约有差异时先列出字段映射与建议，由前端适配服务边界。

## 模型接入后的变化（前端不需要改渲染）

真实模型已接入，但对网页来说 **`/api/mediate` 的响应形状没变**：`plans[] / issues[] / hints[]`
字段完全一致，金额仍然全部是整数分，且 `Σ allocations[].totalCents === payableCents` 照旧成立。
变的只有 `meta`：

| 字段 | 规则版 | 模型版 | 前端怎么用 |
|---|---|---|---|
| `meta.planner` | `rule-based-v2` | `llm-validated-v1` | 「AI 推荐 / 规则兜底」标记，可以不显示 |
| `meta.reasoning` | `rules` | `llm` / `rules-fallback` | 同上 |
| `meta.degraded` | `false` | 模型失败或被拦时为 `true` | **不要据此报错或跳无解页**，方案仍然有效 |
| `meta.llm` | `not_configured` | 模型标识 | 调试用 |
| `meta.llmDetail[]` | `[]` | 逐策略 `accepted/rejected/skipped` + `code` + 耗时 | 调试用，可忽略 |

三条前端要记住的边界：

1. **模型不可用不是错误**：超时、限流（429）、输出非法都会回退规则版，接口照样 `ok: true` + 有效方案，
   只会在 `hints[]` 里多一条非阻塞说明。
2. **`blocking: true` 只代表真的无解**（预算不足、预算买不到主食、复议已无更便宜替代），
   与「模型这次没顶上」无关。
3. 「每人必须有主食」这条规则现在两边都生效：规则版在试算前判定（`no_main_within_budget`），
   模型版在 `model_missing_main` 拦截，前端不需要自己判断。

接口自检：`GET /api/health` 的 `llm` 字段能直接看出模型有没有配置（`AI_*` 三项齐全才显示模型标识）。
