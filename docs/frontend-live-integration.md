# 前端真实接口联调

## 当前分支与范围

`codex/integration` 保留两方历史，合入前端 `f7fc3ba` 与后端 `bb2b9d6`；没有修改 main。
前端接口客户端位于 `apps/web/src/services/live-service.ts`。模型由后端继续接入，此提交没有实际模型调用。

## 用户流程

- 首页「开始饭局」使用真实模式，按城市与关键词调用 `/api/stores`；默认城市北京，可修改，不自动读取定位。
- 门店选择后继续现有成员1—4、预算、份量偏好与角色设置，五页流程与手机优先布局保留。
- 仲裁页调用 `/api/mediate`；服务返回前一直处于等待核对阶段，不用计时器声称真实工具或模型已经完成。
- 结果使用响应里的真实商品目录、图片与试算明细，不再查 Demo 商品 ID。无图时显示品类图标。
- 餐品明细与成员含优惠分摊的实付分开展示，整单小票显示商品合计、优惠及应付；输入预算为元，响应金额为整数分。
- 只展示实际返回的策略，去重策略禁用并标注结果已合并。默认优先和平；未返回和平时选择实际存在的方案。
- 自填要求提示不把有效方案变成无解；接受前仍需核对勾选。名称/标签推导的忌口信息明确标注来源和局限。
- 复议发送上一份完整方案。失败留在弹窗中并保留旧方案；成功才替换方案和成员偏好。
- 接受方案只确认推荐，没有任何创建订单、支付或积分接口调用。

首页「体验三人示例」保留独立离线模式：门店、餐品与价格均标明示例，完全不请求 MCP。
真实模式发生错误时不会静默退回 Demo。返回、重新开始或离开请求页面会取消旧请求，防止旧响应覆盖新页面。
自填文字在角色卡中保留；切回非「其他」要求后，客户端不将隐藏的历史自填内容作为当前要求提交。

## 本轮联调修复

HTTP 隔离联调发现 `/api/mediate` 在低预算时可返回某成员空餐盘，而整单仍标为成功。
已在 `buildPlan` 试算前校验每位成员主食与必须包含类别；不满足时返回阻塞 constraint，不返回成功方案。
主食选择使用当前剩余预算，避免先选必选配餐后仍按完整预算选主食；复议候选同样排除非餐品。
这几处增量在 `apps/server/src/services/mediate.ts`，模型分支合并时请保留。

## 启动

```sh
npm ci
# 复制 .env.example 到 .env，在本地填写 MCD_MCP_TOKEN，密钥不得提交
npm run dev
# 手机预览另开终端；电脑与手机连接同一可信 Wi-Fi
npm run dev:mobile
```

前端 `/api` 通过 Vite 代理到本机服务端。手机访问电脑的 Wi-Fi Network 地址，不能使用手机自己的 127.0.0.1。
本机未配置 MCP 时，真实模式显示服务不可用并可重试，离线示例仍可使用。

## 验证及限制

```sh
npm run check
npm test
npm run test:integration
```

- 前端 19 项离线逻辑检查；后端 26 项离线测试。
- 本机临时 HTTP 服务验证：浏览器 API 客户端 → 生产路由 → 生产推荐服务 → 样例 MCP 依赖。
  覆盖门店、真实目录 ID、201 分优惠分摊、完整旧方案复议、其他成员餐品锁定、人工核对及预算不足。
- React 静态渲染检查：首页、含图片的结果、人工核对、去重策略和缺失输入状态。
- 本机没有服务端 .env，本轮没有重新访问在线麦当劳 MCP；没有运行写订单探针。
- 浏览器自动化在此前被环境策略阻止，本轮没有尝试替代方式；320/360/390/430px 的实际点击、布局与软键盘仍需浏览器或真机确认。

静态渲染与 HTTP 隔离验证不等同于真实 MCP 在线验收或手机视觉验收。
